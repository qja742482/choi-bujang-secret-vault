# BYTE BACK 방어전 시작 틀 R5

이 저장소는 1단계에서 학생 본인이 GitHub 저장소와 Vercel 배포를 만드는 출발점입니다. 포함된 메모 네 건은 가상 자료입니다. 실제 학생 자료, 토큰, 비밀키를 넣지 마세요.

## 학생이 하는 일: 세 걸음

1. GitHub 계정을 만듭니다.
2. 방어전 1단계 카드의 **Deploy** 버튼을 누릅니다. Vercel에 GitHub로 로그인하고, 새 저장소가 **본인 계정의 Public 저장소**인지 확인한 뒤 Deploy를 누릅니다.
3. 배포가 끝나면 화면에 나온 `https://…vercel.app` 주소를 방어전 1단계 카드에 붙여넣고 제출합니다. 저장소 주소나 설정 파일은 적지 않습니다.

배포가 끝나면 `/`에서 점령된 가상 자료실을 볼 수 있습니다. `/data.json`에는 같은 가상 메모가 공개됩니다. 이 공개 상태를 확인하는 것이 1단계의 출발점입니다. 1단계 접수와 심판 판정은 포털에서 확인합니다.

## 시작 틀의 자동 처리

`vercel.json`은 정적 결과물 `public`을 배포합니다. 빌드 명령 `npm run build`는 Vercel이 제공하는 GitHub 저장소 소유자·이름, 커밋 SHA, 배포 URL을 검증하고 `public/aleph.json`을 생성합니다. 이 값이 없으면 빌드가 실패하므로, 성공한 것처럼 빈 주소를 내보내지 않습니다. `aleph.json`의 내용만으로 저장소 소유권이나 방어 성공을 인정하지 않습니다. 심판이 공개 저장소의 실제 커밋과 배포된 자료를 따로 대조해야 합니다.

`aleph.config.json`의 `repoUrl`과 `publicAppUrl`은 이전 제출 묶음 방식의 자리표시자입니다. 1단계에서는 학생이 편집하지 않습니다. 2단계 이후 코딩 도구가 필요한 설정과 보호 기능을 단계별로 작성합니다. `npm run bundle`과 `bundle-notes.json`도 1단계의 세 걸음에는 포함되지 않습니다.

로컬에서 가상 화면만 확인할 때는 `npm run build -- --local`을 사용합니다. 로컬 실행은 Vercel 배포나 심판 접수를 증명하지 않습니다. 저장소의 `src/attack-check.mjs`는 실제 배포가 된 뒤 `/data.json`을 비로그인으로 요청해 공개 가상 메모의 확인 표시를 읽습니다.

## 다음 단계의 코딩 도구에 전달할 규칙

[AGENTS.md](AGENTS.md)를 먼저 읽히고 한 번에 한 제작 단위만 요청하세요. 2단계부터는 자료 보호를 구현할 때 `public/data.json`을 복사하는 1단계 빌드 흐름도 함께 바꿔야 합니다. 3단계 이후의 로그인, 허용 경로, 5단계의 원본 API 주소, 6단계 이후 정책 규칙은 해당 단계 원고와 계약에 맞춰 추가합니다. 비밀번호·토큰·서버 전용 키·실제 학생 기록을 코드, Git, 제출 묶음에 넣지 않습니다.

`src/decider.mjs`와 `src/detect.mjs`의 로컬 시험은 반 엔진이나 운영 심판의 결과가 아닙니다. 1단계 이후 제출 묶음 계약 `aleph.defense.submission.v2`는 `scripts/bundle.mjs`에 남아 있으며, 코딩 도구가 해당 단계의 최신 배포 주소와 Git 원격을 맞춘 뒤 사용합니다.

## 🛡️ 2단계 보안 및 아키텍처 노트

- **서버 API 도입**: 정적 `data.json` 파일 대신 Vercel 서버리스 함수(`/api/memos`)를 통해 데이터를 동적으로 호출합니다.
- **데이터베이스 연동**: Supabase `memos` 테이블과 연동하여 안전한 백엔드 구조의 기틀을 마련했습니다.
- **보안 검토**: 현재 단계에서는 익명 접근 및 공개 API 구조에 따른 보안 취약점 포인트를 확인하고 실습하는 데 초점을 맞추고 있습니다.

### 🔍 2단계 검증 및 공개 API 약점 기록

- **가상 메모 검색 확인 절차**: 현재 배포 파일과 GitHub 최신 소스 코드 파일에서 실습용 가상 메모 문장이 포함되어 있는지 검색하여 확인합니다.
- **과거 노출 잔류 경고**: Git 히스토리(옛 공개 커밋)나 이전 배포 버전(옛 배포)이 남아 있는 한, 과거 데이터 노출 이력이 완전히 해소되었다고 간주하지 않습니다.
- **검색 결과 및 남은 약점 기록**:
  - **검색 결과**: 최신 배포 및 브랜치에서 정적 파일(`data.json`)이 제거되고 API 엔드포인트로 전환된 상태를 확인합니다.
  - **공개 API의 남은 약점**: 현재 API 엔드포인트는 인증 없이 누구나 접근 가능한 공개 주소 형태라는 약점이 존재함을 기록합니다.

  ## 🔍 3단계: 가상 메모 노출 검증 및 공개 API 약점 기록

### 1. 가상 메모 문장 검색 및 확인 절차
- **검색 대상**: 현재 Vercel 배포 파일 및 GitHub 최신 소스코드(`main` 브랜치).
- **검색 결과**: `public/data.json` 정적 파일이 제거되었으며, 클라이언트 코드 및 정적 빌드 결과물 내에 실습용 가상 메모 텍스트 문장이 직접 포함되어 있지 않음을 확인했습니다.

### 2. 과거 노출 이력에 대한 주의사항 (잔류 경고)
- **과거 노출 미해소 안내**: 최신 커밋 및 현행 배포에서 정적 파일이 삭제되었더라도, 이전 Git 커밋 히스토리(옛 공개 커밋)나 기존 Vercel 배포 이력(옛 배포)에는 과거의 데이터가 그대로 남아 있을 수 있습니다.
- 따라서 이전 커밋/배포가 존재하는 한 과거 데이터 노출 이력이 완전히 해소된 것으로 간주하지 않으며, 필요 시 히스토리 정리 작업이 병행되어야 함을 기록합니다.

### 3. 공개 API의 남은 보안 약점
- **익명 접근 가능**: 현재 Vercel 서버리스 함수(`/api/memos`)는 별도의 인증(Authentication) 및 인가(Authorization) 처리가 되어 있지 않아, API 주소만 알면 누구나 데이터를 조회할 수 있는 공개(Public) 엔드포인트 형태입니다.
- **향후 과제**: 다음 단계에서 사용자 인증 및 접근 제어(RLS / Session / Token) 조치를 추가하여 데이터 접근을 차단해야 합니다.

## 🔍 6단계: 등록한 기기만 자료실에 들어옵니다 (Device Registration)

### 1. 판정기 규칙 구현
- `src/decider.mjs`에 `device_registered` 규칙을 추가했습니다.
- 요청 객체의 `request.deviceRegistered` 값이 참(`true`)일 때만 자료실 접근을 허용하고, 미등록이거나 값이 없는 경우 거부(`deny`, `reasonCode: 'device_not_registered'`)하도록 보안 로직을 적용했습니다.

### 2. 검증 테스트 실행 결과
- 터미널에서 `npm run decider:test` 명령어를 실행하여 아래와 같이 정상 요청 통과 및 미등록 기기 차단 결과를 확인했습니다.
  - **통과 · 등록 기기의 정상 요청**
  - **통과 · 미등록 기기의 가상 요청 (`deny` · `device_not_registered`)**

### 3. 설정 변경
- `aleph.config.json`의 `step` 값을 `6`으로 업데이트하여 요구사항에 맞추었습니다.

## 🔍 10단계: 백업에서 자료실을 되살립니다 (Backup & Recovery Validation)

### 1. 안전 정책 사본 검증 및 복구 순서
- **사본 재검증 및 버전 대조**: 안전 정책 사본(`src/decider.mjs` 규칙, `allowedRoutes`, DB 접근 정책)을 다시 읽어 버전을 대조합니다. 사본이 없거나 검증에 실패하면 멈추며 실행 전 버전과 변경 항목을 표시합니다.
- **시험 계정 B의 단건 메모 복구 및 재확인**: 시험 계정 B의 가상 메모 한 건을 지정하고, 복구한 메모를 다시 읽고 사본과 ID·소유자·내용 해시를 대조하여 세 값이 모두 일치할 때만 그 한 건을 복원합니다. 다른 메모와 감사 기록은 보존합니다.

### 2. 복구 뒤 재시험 순서
- **정상·금지 요청 재시험**: 복구 뒤 1~9단계의 정상 요청 허용과 1~9단계 금지 요청 거부를 각각 확인합니다. 실행하지 않은 시험은 미실행으로 둡니다.

## 📱 11단계: 나만의 접속 앱을 완성합니다 (PWA Manifest & Server-Side Device Approval)

### 1. 설치형 웹앱 설정 및 기기 승인 상태 표시 (만들기 1)
- **Manifest 및 상태 표시**: PWA 스타일의 매니페스트 설정을 적용하고 앱 이름과 오프라인 안내를 포함합니다. 단, 단순 설치 여부만으로 기기 승인이 완료되었다고 처리하지 않습니다.
- **기존 보호 유지**: 새로운 접속 화면에서도 기존 보호 요청의 정상 및 거부 결과가 철저히 유지되도록 구성합니다.

### 2. 서버 기반 기기 승인 및 권한 제어 (만들기 2)
- **서버 중심 승인**: 기기 승인 여부는 클라이언트가 임의로 결정하지 않고 **서버와 판정기**가 검증하며 결정합니다. 기기 키나 토큰은 브라우저 저장소(`localStorage` 등)에 저장하지 않습니다.
- **승인 전 자료 차단**: 서버가 정식 등록 기기로 확인한 후에만 기존 자료실을 열어주며, 승인 전에는 보호된 자료를 절대 노출하지 않습니다.

### 3. 서명 검증 및 요청 변조 방지 (만들기 3)
- **서버 서명 검증**: 클라이언트 요청에 대한 엄격한 서명 검증을 거쳐 요청의 진위성을 확인합니다.
- **경로 및 본문 변조 차단**: 서명 이후 임의로 요청 경로를 변경하거나 본문을 수정하는 시도를 서버와 판정기가 감지하여 거부합니다.
